# Tailscale 모니터링

Tailscale에 붙은 장비의 이름·태그가 팀 규칙을 지키는지 자동으로 확인하고, 누가 언제 무엇을 바꿨는지 Slack으로 알려 주는 작은 웹 서비스입니다.

---

## 왜 만들었나

우리 회사에는 사내 서버가 없습니다. 하드웨어팀과 AI팀은 사무실도 나뉘어 있어서, 사무실 장비와 현장에 설치한 장비를 모두 Tailscale로 묶어 쓰고 있었습니다.

처음에는 이 정도로 충분했지만, 장비가 늘면서 관리가 무너지기 시작했습니다.

- **계정 하나를 여럿이 같이 썼습니다.** 하드웨어팀이 Tailscale 계정 하나를 공유했기 때문에, 장비를 누가 등록했는지·누가 지웠는지 알 수 없었습니다.
- **현장 실증 장비가 빠르게 늘었습니다.** 현장에 장비를 설치할 때마다 터널링용으로 붙이고, AI팀이 "우리도 끼워 달라"고 하면 또 붙이다 보니 장비 이름도 태그도 사람마다 제각각이 됐습니다.
- **권한이 섞였습니다.** Tailscale은 태그로 접근 권한을 정하는데,
  - 태그가 없는 장비는 등록한 계정(=공유 계정)의 권한을 그대로 받고,
  - 태그를 여러 개 붙이면 각 태그의 권한이 합쳐집니다.
  
  현장 장비에 팀 태그가 하나 더 붙으면 현장 장비가 사무실 내부망까지 들어올 수 있게 되는 식이었습니다.
- **문제를 알게 되는 건 늘 사고가 난 뒤였습니다.** 관리 콘솔을 하루 종일 들여다볼 수는 없으니, 이상한 장비나 잘못된 태그는 누군가 우연히 발견할 때까지 그대로 남았습니다.

규칙을 정하는 것만으로는 해결되지 않았습니다. 규칙이 복잡하면 아무도 지키지 않고, 지켰는지 확인할 사람도 없었기 때문입니다. 그래서 **규칙은 최대한 단순하게 정하고, 지켰는지는 사람이 아니라 프로그램이 확인하게** 만들기로 했습니다.

## 그래서 정한 규칙

| 항목 | 규칙 |
|---|---|
| 장비 이름 | `장비-지역-닉네임` (예: `jetson-site1-sensor01`, `desktop-office-kim`, `mobile1-office-lee`) |
| 지역 | 사무실 장비는 `office`, 현장 장비는 설치 지역 이름 |
| 태그 | 장비 하나에 **태그 하나만**. 지역이 `office`면 `tag:office`, 그 외는 `tag:field` |
| 접근 정책 | 현장(`field`) 장비는 사무실(`office`) 장비에 정해 둔 몇 개 포트로만 접속 (Tailscale 정책 파일에서 설정) |

태그를 팀·용도별로 세세하게 나누던 방식을 버리고 **"사무실 장비냐, 현장 장비냐" 두 가지로만** 나눴습니다. 현장 장비는 밖에 있어 분실·탈취 위험이 크니 사무실 망과 분리하는 것, 그것 하나만 확실히 지키자는 생각입니다. 세세한 분류는 이름과 웹의 그룹 기능으로 충분합니다.

## 어떻게 감지하나

```
Tailscale API ──(60초마다 읽기)──▶ 모니터링 서버 ──▶ 웹 화면
  · 장비 목록                         · 규칙 검사            · Slack / Telegram 알림
  · 설정 변경 감사 로그                · 변경 이력 기록
```

- **읽기 전용입니다.** Tailscale에서 읽기 권한 2개(`devices:core:read`, `logs:configuration:read`)만 받은 OAuth 키를 씁니다. 이 프로그램은 Tailscale의 장비나 정책을 절대 바꾸지 않습니다. 잘못 동작해도 네트워크에는 영향이 없습니다.
- **장비 목록**으로 지금 붙어 있는 장비의 이름·태그·접속 상태를 보고 규칙 위반을 판정합니다.
- **설정 변경 감사 로그(Configuration audit log)**로 누가, 언제, 어디서(관리 콘솔·API·장비) 무엇을 바꿨는지 가져옵니다. 장비 등록·삭제, 태그·이름 변경, 정책 파일 변경까지 다 여기에 남습니다.
- **왜 폴링(주기적으로 읽기)인가:** Tailscale에도 이벤트를 보내 주는 웹훅이 있지만, ① 받으려면 인터넷에 공개된 주소가 필요하고(우리는 공개 서버가 없음), ② 태그 변경 이벤트가 없습니다. 60초마다 직접 읽으면 공개 주소 없이도 모든 변경을 놓치지 않고, 서버가 잠깐 꺼졌다 켜져도 밀린 기록을 다시 가져올 수 있습니다.
- 회선이 느려 연결이 가끔 끊기면 자동으로 다시 시도합니다. API가 실패한 것을 "장비가 사라졌다"로 오해하지 않습니다.

## 기능과 넣은 이유

| 기능 | 하는 일 | 넣은 이유 |
|---|---|---|
| **규칙 위반 감지** | 이름 형식, 태그 없음, 태그 규칙(office/field) 위반을 찾아 빨갛게 표시 | 태그 없는 장비는 공유 계정 권한을, 태그가 여러 개면 합쳐진 권한을 받기 때문 |
| **변경 이력** | 장비 등록·삭제, 태그·이름·키 만료 변경, 정책 변경을 **누가 했는지**와 함께 기록 | 공유 계정 시절 "이거 누가 지웠어?"에 답할 수 없었음 |
| **변경 알림** | 위 변경이 생기면 Slack·Telegram으로 바로 알림 | 콘솔을 보고 있지 않아도 이상한 변경을 바로 알기 위해 |
| **예외 장비** | 팀이 허용한 장비는 "알림 제외"로 검사에서 뺌 | 정당한 예외가 계속 위반으로 울리면 알림 자체를 안 보게 됨 |
| **사용자 그룹 (2단계)** | 장비를 `팀 › 사람`처럼 묶어서 보기. 서버에 저장되어 모두 같은 화면을 봄 | 태그는 두 개로 줄였지만, 관리할 때는 팀·사람별로 보고 싶음 |
| **규칙 설명 카드** | 장비 화면에 지금 규칙을 사람 말로 적어 두고 바로 수정 | 정규식은 아무도 읽지 않음. 처음 장비를 붙이는 사람이 바로 이해해야 함 |
| **접속 상태·키 만료 임박** | 마지막 접속 시각, 키 만료 2주 전 표시 | 현장 장비는 키가 만료되면 조용히 끊김 |
| **웹 업데이트 버튼** | 새 버전이 나오면 알림이 오고, 웹에서 버튼 한 번으로 교체 | 업데이트할 때마다 서버에 들어가 명령어를 치지 않기 위해 |

## Slack·Telegram 알림을 넣은 이유

웹 화면은 아무도 계속 열어 두지 않습니다. 그래서 **팀이 이미 하루 종일 보고 있는 Slack으로 알림이 가야** 의미가 있다고 봤습니다.

- **Slack Incoming Webhook을 쓴 이유:** 봇이나 앱을 만들 필요 없이 주소 하나로 정해진 채널에 메시지를 보낼 수 있는 가장 간단한 방법입니다. 그 채널에 글을 쓰는 것 외에는 아무 권한도 없어서, 주소가 새어도 피해 범위가 작습니다.
- **Telegram은 개인 테스트용입니다.** 규칙을 바꾸거나 새 기능을 넣을 때 먼저 내 Telegram으로 받아 보고, 괜찮으면 팀 Slack을 켭니다. 팀 채널을 테스트 메시지로 어지럽히지 않기 위한 2단계입니다.
- **알림 피로를 줄이는 장치:**
  - 같은 위반이 계속되는 동안에는 다시 보내지 않습니다. 고쳐졌다가 다시 생기면 그때 다시 알립니다.
  - "이름 규칙 위반 / 태그 규칙 위반 / 변경 내역"을 종류별로 묶어 한 메시지로 보냅니다.
  - 알림에는 정규식 같은 기술적인 내용 없이 "이름 규칙 불일치", "태그 규칙 불일치" 정도만 적고, 자세한 이유는 웹에서 봅니다.
  - 메시지 아래 **[Tailscale 콘솔] [모니터링 열기]** 버튼으로 바로 고치러 갈 수 있습니다.
- 채널 전송이 실패하면 쌓아 두었다가 다시 보냅니다. 한 채널이 고장 나도 다른 채널은 영향을 받지 않습니다.

## 어떻게 관리하나

- **운영:** 사무실 서버 한 대에서 Docker로 `monitor`(웹·수집)와 `updater`(업데이트 담당) 두 컨테이너가 돕니다. 웹은 **Tailscale 안에서만** 열리고, 로그인이 필요합니다.
- **규칙 바꾸기:** 웹의 규칙 카드에서 바로 바꾸면 모든 장비를 즉시 다시 검사합니다.
- **새 버전 배포:** 개발 PC에서 이미지를 사내 레지스트리에 올리면 → 서버가 10분 안에 새 버전을 발견해 Slack으로 알리고 → 웹 상단의 **업데이트** 버튼을 누르면 몇 초 만에 교체됩니다. 기록과 설정은 그대로 남습니다.
- **비밀값 보관:** Tailscale·Slack·Telegram 연동 정보는 웹에서 입력하고, 서버 DB에 암호화(AES-256-GCM)해 보관합니다. 코드 저장소나 Docker 이미지에는 들어가지 않습니다.

## 만들고 나서 좋아진 점

- **"누가 바꿨지?"를 묻지 않게 됐습니다.** 장비 등록·삭제, 태그·이름·정책 변경이 바뀐 사람과 함께 Slack에 바로 올라옵니다.
- **장비 이름과 태그가 실제로 정리됐습니다.** 규칙을 정하고 위반 목록을 보면서 하나씩 고쳤고, 새로 붙는 장비가 규칙을 어기면 바로 알림이 오니 다시 흐트러지지 않습니다.
- **현장 장비와 사무실 망이 분리됐는지 눈으로 확인할 수 있습니다.** 태그가 `office`/`field` 하나씩만 붙어 있는지가 화면에 바로 보입니다.
- **정책 파일 실수를 빨리 알아챕니다.** 정책이 바뀌면 몇 줄이 바뀌었는지, 누가 바꿨는지 알림이 오고, 이력에서 언제 바뀌었는지 찾을 수 있습니다.
- **관리 콘솔을 일부러 찾아보지 않아도 됩니다.** 볼 일이 생기면 알림이 먼저 옵니다.
- **업데이트가 버튼 하나로 끝납니다.**

## 한계

- 장비별로 Funnel(인터넷 공개)이 켜졌는지는 Tailscale API로 확인할 수 없어 감지하지 못합니다. Funnel은 정책 파일에서 허용할 장비를 제한하는 방식으로 막습니다.
- 공유 계정으로 작업하면 이력의 "누가"도 공유 계정으로만 남습니다. 사람마다 개인 계정을 쓰는 것이 가장 좋습니다.
- 모니터링 서버가 꺼져 있는 동안에는 알림이 오지 않습니다. 다시 켜지면 밀린 변경을 이력에 채웁니다.
- 트래픽 분석이나 침입 탐지 도구가 아닙니다. 설정 변경을 지켜보는 도구입니다.

## 실행 방법

### 데모로 먼저 보기

Node.js 24(24.16 이상)가 필요합니다. 외부 패키지가 없어 `npm install`은 하지 않아도 됩니다.

```bash
npm run demo
```

http://127.0.0.1:8787 을 열면 가상 데이터로 화면을 볼 수 있습니다. 실제 Tailscale·Slack·Telegram에는 아무 요청도 보내지 않습니다.

### 실제 연동

1. Tailscale 관리 콘솔 → Settings → Trust credentials → OAuth에서 읽기 권한 `devices:core:read`, `logs:configuration:read` 두 개로 키를 만듭니다.
2. `.env.example`을 `.env`로 복사하고 `npm start`로 실행합니다.
3. 웹의 **규칙·알림 → 연동 설정**에 Tailscale(Tailnet, Client ID, Client Secret), Slack(Incoming Webhook 주소), Telegram(Bot Token, Chat ID)을 입력합니다. 저장하면 재시작 없이 바로 적용됩니다.
4. 규칙 카드에서 팀 규칙을 저장합니다.

Telegram은 개인 대화라면 먼저 봇에게 `/start`를 보내야 메시지를 받을 수 있습니다.

### Docker로 서버에 올리기

서버 폴더에 `compose.yaml`, `.env`, `.data/`를 둡니다.

| `.env` 키 | 설명 |
|---|---|
| `UPDATE_IMAGE`, `MONITOR_TAG` | 이미지 주소(태그 제외)와 실행할 버전. 웹 업데이트가 `MONITOR_TAG`를 바꿉니다 |
| `DOCKER_AUTH_FILE` | 서버에서 `docker login` 해 둔 `config.json` 경로. 새 버전 확인과 이미지 받기에 읽기 전용으로 씁니다 |
| `UPDATER_TOKEN` | 모니터링 ↔ 업데이터 내부 인증용 무작위 값(16자 이상) |
| `MONITOR_HOST_IP` | 포트를 열 서버의 Tailscale IP (Tailscale 안에서만 접속되게) |
| `MONITOR_USER`, `MONITOR_PASSWORD` | 웹 로그인 |
| `MONITOR_ALLOWED_HOSTS`, `MONITOR_PUBLIC_URL` | 접속을 허용할 주소, 알림의 "모니터링 열기" 버튼 주소 |

```bash
docker login <레지스트리>
docker compose up -d
docker compose logs --tail=50 monitor updater
```

`.data`는 컨테이너 사용자(uid 1000)가 쓸 수 있어야 합니다. 기록을 옮길 때는 서버를 멈춘 상태에서 `.data` 폴더 전체(`monitor.sqlite`, `credentials.key`)를 함께 옮기세요.

### 새 버전 올리기

```bash
# package.json의 version을 올린 뒤
docker build --platform linux/amd64 -t <레지스트리>/<저장소>:<버전> .
docker push <레지스트리>/<저장소>:<버전>
```

10분 안에 서버가 새 버전을 알리고, 웹의 **업데이트** 버튼으로 적용합니다. 되돌리려면 `.env`의 `MONITOR_TAG`를 이전 버전으로 고치고 `docker compose up -d monitor`를 실행합니다. 업데이터 코드가 바뀐 버전은 서버에서 `docker compose up -d`를 한 번 실행해야 합니다.

### 테스트

```bash
npm test
npm run check
```

실제 서버를 띄워 HTTP로 사용자 시나리오(로그인, 장비 등록·태그 변경·삭제, 예외 처리, 채널 켜고 끄기, 업데이트)를 돌리는 E2E 테스트가 포함되어 있습니다. 모두 가짜 Tailscale API와 가짜 Slack·Telegram을 써서, 실제 서비스에는 아무것도 보내지 않습니다.
